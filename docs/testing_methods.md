# Методы тестирования

## Сравнение методов в ЛР №4

| Метод | Как применён | Преимущество | Ограничение |
| --- | --- | --- | --- |
| Эквивалентное разбиение | Проверены допустимые размеры и некорректные входные данные | Позволяет выбрать типичные случаи из каждого класса | Ошибки внутри класса могут остаться незамеченными |
| Анализ граничных значений | Проверены размеры 0 и 1 | Выявляет ошибки на границе допустимых размеров | Проверяет только выбранные границы |
| Покрытие строк и ветвей | Проверены обычный запуск и ветви обработки ошибок | Показывает, какие части кода выполнялись | Требует отдельных проверок ожидаемого результата |
| Комбинации условий | Проверены четыре пары для условия `rows <= 0 or columns <= 0` | Проверяет совместное влияние двух условий | Число комбинаций растёт с числом условий |
| Интеграционное тестирование | Проверена передача запроса и результата через JSON | Выявляет ошибки взаимодействия модулей | Причину сбоя бывает сложнее локализовать |
| Регрессионное тестирование | Проверены повторный запуск и ошибка дочернего процесса | Помогает сохранить уже проверенное поведение при изменениях | Требует добавлять сценарии для новых случаев |

Для проверки входных данных подходят граничные значения и эквивалентное
разбиение. Для составных условий нужны явные комбинации входов. Обмен
через файлы и запуск дочернего процесса стоит проверять интеграционными
тестами, а важные сценарии повторять при каждом изменении в CI.

## Ревью тестов

- Проверены ожидаемые результаты для допустимых и ошибочных входных данных.
- JSON-файлы создаются во временных каталогах `tmp_path`.
- В ошибочных сценариях проверяются тип исключения и отсутствие выходного файла.
- Регрессионные тесты проверяют перезапись результата и передачу ошибки
  из дочернего процесса.
- GitHub Actions запускает тесты при `push` и `pull_request` на Ubuntu и Windows.
- Итог проверки — 50 тестов прошли, покрытие 100%, Flake8 без замечаний.

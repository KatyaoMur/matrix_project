# Сравнение стратегий интеграции

| Стратегия | Преимущества | Недостатки | Когда применять |
|---|---|---|---|
| Нисходящая | Рано проверяется управление системой и общий сценарий | Нужны заглушки нижних модулей, реальные вычисления проверяются позднее | Системы с важной управляющей логикой и интерфейсом |
| Восходящая | Рано проверяются реальные вычисления и базовые компоненты | Нужны тестовые драйверы, общий сценарий появляется позднее | Библиотеки, расчётные программы, системы с готовыми нижними модулями |
| Сэндвич | Верхние и нижние уровни можно проверять параллельно | Сложнее координация, могут потребоваться драйверы и заглушки | Крупные многоуровневые системы |
| Риск-ориентированная | Наиболее опасные взаимодействия проверяются раньше | Требуется правильная оценка рисков и зависимостей | Проекты с внешними сервисами и сложными компонентами |
| Функционально-ориентированная | Рано появляются законченные пользовательские функции | Общие компоненты могут затрагиваться несколько раз | Прикладные системы с независимыми сценариями |
| Т-образная | Рано проверяется сквозной путь через уровни системы | Первый вертикальный срез требует участия многих компонентов | Проверка архитектуры и технологий нового проекта |

## Выбор для проекта

Для варианта 20 задана восходящая интеграция.
Она соответствует состоянию проекта: расчёт и форматирование
были выделены в модули и имели отдельные тесты.

Сначала проверены нижние модули, затем подключён main.
На следующем этапе введён обмен через JSON-файлы.
После проверки общей цепочки добавлены запуск отдельного процесса,
обработка отказов и автоматическая проверка интеграции.

Для данного учебного проекта восходящая стратегия позволяет
использовать готовые функции без заглушек.
Тесты выполняют роль драйверов.
